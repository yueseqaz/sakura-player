# 两小时长视频实测指南

状态：交由用户实测，尚未通过验收。短样本自动化不能代替这项测试。

## 准备

1. 使用本轮或更新的开发构建，在 `Window > Diagnostics…` 记录版本和 build。
2. 选一部本机磁盘上的、超过两小时十分钟的视频。当前应用仍用 AVFoundation，建议先用能正常打开的 MP4/H.264/AAC；MKV/WebM 的 libmpv 探针结果不代表应用已经支持。
3. 优先选有清楚对白、口型或拍手声的片段，便于判断音画同步。不要上传视频、字幕或完整文件路径。
4. 关闭其他播放器和高负载程序，保持供电。打开“活动监视器”，搜索 `SakuraPlayer`，观察 CPU 和内存。
5. 打开视频，选择从头播放、1 倍速和一种固定字幕设置。前两小时不要拖动、切换视频或更改倍速，以保留一条连续播放基线。

可选：在终端运行以下命令，在测试期间阻止 Mac 自动睡眠（不需要管理员权限）：

```bash
caffeinate -di -t 7500
```

命令持续约 125 分钟；提前结束时在该终端按 `Ctrl-C`。不要合上笔记本盖子。无需安装 Xcode 或 Instruments 即可完成基础检查。

## 连续播放阶段

预热五分钟后记第一笔，随后在 30、60、90、120 分钟各记录一次：

| 实际经过时间 | 视频时间 | CPU % | 内存 MB | 口型/声音同步 | 字幕、画面和异常 |
| --- | --- | --- | --- | --- | --- |
| 5 分钟（预热后） | | | | | |
| 30 分钟 | | | | | |
| 60 分钟 | | | | | |
| 90 分钟 | | | | | |
| 120 分钟 | | | | | |

- 使用同一活动监视器指标，最好截下每次读数。CPU 的 100% 约代表一个逻辑核心，并不等于整机满载。
- 少量内存上升可能来自缓存；重点看预热之后是否每次都持续大幅增长，不能仅凭一次读数判定泄漏。
- 在对白或清晰瞬态声音处观察是否逐渐失步；如果不确定，写“不确定”，不用猜毫秒数。
- 记录崩溃、无声、黑屏、连续掉帧、卡死、字幕消失或控制栏闪烁发生的大致视频时间。

## 两小时之后的交互回归

连续基线结束后再做，避免把交互干扰混进两小时数据：

1. 暂停、继续；静音后调高音量，确认声音确实恢复。
2. 连续拖动时间轴到前、中、后部各几次；以最后一次松手的位置为准，观察有没有跳回旧位置或长时间不恢复。
3. 播放中持续移动鼠标十秒，再停下；控制栏应保持稳定，然后按设置延迟隐藏。拖动时不能隐藏。
4. 切换窗口/全屏并调整窗口比例。默认 Fill 保持等比裁切并铺满；Fit 模式保留完整画面时可能有黑边，这是两种模式的正常区别。
5. 有外挂字幕时，关闭后等待原字幕时间段，确认不会重新冒出；将延迟设为 +0.5 秒，应比原来更晚出现，再重置为 0。
6. 快速打开其他可播放文件约十次，再关闭当前视频。观察旧音频是否停止、待机 CPU 是否回落、内存是否趋于稳定。缓存不一定立即全部释放。
7. 重新打开测试文件，检查继续播放的位置是否合理。

基础验收目标是连续两小时不崩溃、不持续无界增长、不明显失步；即使通过，也不能据此推断所有编码、HDR 或其他 Mac 都通过。异常的内存趋势还需要开发侧用 Instruments 进一步定位。
